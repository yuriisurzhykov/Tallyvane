# Управление схемами аутентификации: целевой UX администратора

Статус: согласованный ориентир для интерфейса. Интерактивный пример: [auth-policy-guided.html](prototypes/auth-policy-guided.html). Доменная модель и инварианты безопасности описаны в [спецификации схем](../superpowers/specs/2026-09-25-composable-authentication-tokens-and-schemes-design.md). Если пример и доменная спецификация расходятся, реализация должна сохранить доменные инварианты и уточнить UX.

## Цель экрана

Администратор должен ответить на два вопроса без знания внутреннего формата политики:

1. Чем пользователь может подтвердить конкретное действие?
2. Какой из доступных путей система потребует, если у пользователя есть несколько способов подтверждения?

Экран не управляет секретами, выданными кодами, access/refresh токенами или учётными данными отдельных пользователей. Здесь «токен» — **вид доказательства**: пароль, Google, код входа по email, код приложения, email как второй фактор или резервный код.

## Простая ментальная модель

- **Действие** — что защищаем: вход, смену основного способа входа или управление вторыми факторами.
- **Путь (схема)** — один допустимый способ подтвердить это действие. Например, `Пароль + Код приложения`.
- **Внутри одного пути — «И»**: пользователь подтверждает все указанные способы.
- **Несколько путей для действия — альтернативы**: например, `Пароль + Код приложения` и `Google + Код приложения`.
- **Уровень — явный приоритет**, а не автоматически вычисленная «сила». Если пользователю доступны пути разных уровней, система потребует доступный путь с максимальным уровнем. Если максимальный уровень одинаков, пользователь может выбрать между такими путями.

Слово «путь» используется в интерфейсе как понятное администратору название схемы. В API и доменной модели остаётся `AuthenticationScheme`.

## Структура экрана

1. Слева — выбор защищаемого действия и список уже добавленных путей **только для этого действия**. У каждого пути видны состав, уровень и состояние «включён/выключен».
2. Справа — пошаговая настройка выбранного пути. При открытии существующего пути показываются те же шаги с текущими значениями.
3. Внизу — результат проверки и единое сохранение версии политики. Все изменения до сохранения считаются черновиком; при конфликте версий экран предлагает перечитать политику, а не молча перезаписывает чужую правку.
4. Сброс факторов отдельного пользователя остаётся отдельной административной операцией, не смешанной с редактированием общих правил.

## Основной сценарий: добавить путь

### 1. Выбрать действие

Администратор выбирает «Вход», «Смена способа входа» или «Управление факторами». Список сразу показывает текущие альтернативы. Кнопка **«Добавить допустимый путь»** начинает создание ровно одной схемы для выбранного действия.

Пример: выбрано «Вход». Уже есть `Пароль · уровень 1` и `Пароль + Код приложения · уровень 2`.

### 2. Собрать подтверждения

Сначала выбирается **один основной способ**: пароль, Google или код входа по email. Затем при необходимости добавляется второй фактор: код приложения, email как второй фактор или резервный код. Интерфейс сразу пишет результат естественным языком: «Получится: Пароль + Код приложения. Оба подтверждения обязательны».

Такой порядок особенно важен для входа: сначала пользователь начинает вход основным способом, затем сервер может запросить оставшееся подтверждение. Для двух других действий интерфейс также показывает состав пути, но окончательная допустимость сочетания определяется общей серверной валидацией политики.

Текущий HTML-пример показывает не более одного дополнительного фактора ради ясности взаимодействия. Доменный контракт хранит набор видов доказательств; если для продукта потребуется больше одного дополнительного доказательства, шаг 2 можно расширить до списка без изменения модели «все внутри пути обязательны».

### 3. Задать уровень

Администратор выбирает уровень доверия. Возле выбора нужен короткий смысл: «При нескольких доступных путях система потребует путь с самым высоким уровнем». Не следует подписывать уровень 2 как «двухфакторный» автоматически: уровень — самостоятельное значение политики. В интерфейсе можно показывать уровни 1, 2, 3 как быстрый выбор, но API поддерживает целое положительное значение; произвольный уровень нужен в расширенном редактировании, если политика уже содержит другие значения.

### 4. Проверить результат

Экран показывает человеческое резюме: «Для входа: Пароль + Код приложения, уровень 2». Проверка должна также предупреждать, если этот путь вытеснит другой путь для пользователей, у которых доступны оба, или если изменение оставит действие без рабочего пути.

Кнопка **«Готово»** возвращает к списку выбранного действия. Чтобы разрешить ещё один способ, администратор снова нажимает «Добавить допустимый путь». Это объясняет, как создаются *все* схемы: по одной схеме на каждую альтернативу, повторением одного короткого сценария.

### 5. Сохранить политику

Сохранение отправляет всю новую версию политики. Перед ним проверяются ошибки и потенциальные блокировки. Успех показывает новую версию и подтверждение сохранения. Ошибка оставляет черновик на экране. Для рискованного сочетания «код входа по email + email как второй фактор» требуется отдельное явное подтверждение, предусмотренное действующей политикой.

## Примеры настройки

### Пример A: обычный вход и усиленный вход

| Действие | Путь | Уровень | Что произойдёт |
| --- | --- | ---: | --- |
| Вход | Пароль | 1 | Пользователь без второго фактора входит по паролю. |
| Вход | Пароль + Код приложения | 2 | Пользователь с настроенным приложением подтверждает оба шага до выдачи сессии. |

Это **две схемы**, добавленные по очереди. Вторая не редактирует и не заменяет первую. Путь уровня 1 нужен, чтобы отсутствие настроенного второго фактора не блокировало вход.

### Пример B: несколько способов начать вход

| Действие | Путь | Уровень |
| --- | --- | ---: |
| Вход | Пароль | 1 |
| Вход | Google | 1 |
| Вход | Код входа по email | 1 |

Администратор трижды повторяет создание пути. Пользователь видит только способы, которые действительно доступны его учётной записи. Вход через Google не требует пароль, потому что пароль не входит в этот путь.

### Пример C: управление факторами у пользователя без пароля

| Действие | Путь | Уровень |
| --- | --- | ---: |
| Управление факторами | Код входа по email | 1 |
| Управление факторами | Пароль + Код приложения | 2 |

У пользователя есть только вход по email и нет пароля. Перед подключением приложения у него доступен первый путь; система не просит несуществующий пароль. У пользователя с паролем и уже настроенным приложением может быть доступен второй, более высокий путь. Новый фактор не считается доказательством для собственного подключения: доступные факторы определяются **до** изменения.

### Пример D: равный уровень

| Действие | Путь | Уровень |
| --- | --- | ---: |
| Смена способа входа | Пароль + Код приложения | 2 |
| Смена способа входа | Google + Код приложения | 2 |

Если пользователю доступны оба пути, он может выбрать один из них. Если доступен только один — показывается он. Путь уровня 1 не предлагается как запасной при наличии доступного пути уровня 2.

## Состояния и ограничения интерфейса

| Ситуация | Поведение |
| --- | --- |
| Новый путь не заполнен | Показывать локальную ошибку у обязательного основного способа; не сохранять незавершённый черновик. |
| Удалён последний активный путь входа | Запретить сохранение и объяснить, что пользователям нужен хотя бы один способ входа. |
| Для включённого основного способа нет пути входа без второго фактора | Запретить сохранение: пользователи без настроенного фактора не должны быть заперты. |
| Сочетание способов недопустимо | Показать причину рядом с выбором и оставить сделанные значения для исправления. Источник истины — серверная валидация. |
| Изменена политика другим администратором | Показать конфликт версии, предложить загрузить актуальную политику и сравнить изменения перед повторным сохранением. |
| Ошибка сети или сервера | Сохранить черновик на экране и дать повторить отправку. |
| Рискованное сочетание email-кодов | Показать отдельное подтверждение риска перед сохранением. |
| Ни один путь не подходит конкретному пользователю для защищённого действия | Пользовательский сценарий ведёт к восстановлению или административному сбросу; экран настройки не обещает автоматический обход уровней. |

При удалении схемы полезно показать, какое действие она защищала, её состав и уровень. Если удаление может изменить доступные пользователям варианты, предупреждение должно быть предметным. Для простого изменения названия или порядка строк отдельное предупреждение не требуется.

## Почему один flow, а не три редактора

Проверенный с пользователем макет показал, что отдельные «по действию», «готовые уровни» и «матрица» создавали ложное впечатление разных сущностей. Во всех трёх случаях настраивалась одна и та же схема. Целевой экран поэтому имеет один повторяемый путь создания. Готовые варианты могут позже стать кнопками предзаполнения внутри шага 2, но не самостоятельным режимом. Матрица уместна лишь как будущий обзор большой политики, если реальное число схем сделает обычный список неудобным; сейчас она не нужна.

## Граница макета и реализации

HTML рядом с этим документом открывается локально в браузере и позволяет пройти основные шаги. Он не вызывает API, не хранит данные между открытиями, не моделирует все серверные проверки и не управляет настоящими аккаунтами. Это **эталон взаимодействия**, а не готовый компонент.

При реализации следует использовать существующий экран `frontend-admin/src/views/admin-authentication/ui/AdminAuthenticationView.tsx`, общие UI-компоненты `frontend-shared` и существующую точку сохранения версии политики. Сценарий и его состояние относятся к экрану администрирования; общие поля, кнопки, уведомления и подтверждающий drawer остаются общими компонентами. Схему можно менять глобально через политику, локально через конфигурацию конкретного действия, а временный черновик не меняет сервер до сохранения.
