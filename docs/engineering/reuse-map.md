# Как добавлять фичи на основе существующего кода

Начните с ответственности: ввод и отправка данных, уведомление, переход состояния,
доменное решение или обращение к внешней системе. Затем найдите существующий контракт
и пример ниже. Правила проектирования находятся в [AGENTS.md](../../AGENTS.md).
Эта карта указывает на реализацию; она не заменяет документацию её публичного API.

## Рабочий порядок

1. Опишите пользовательский сценарий, состояния и ошибки. Отделите доменные правила
   от механики UI, транспорта и хранения.
2. Найдите решение в карте, его публичный API, тест и реального потребителя.
   Проверьте ограничения: похожее название ещё не означает подходящий контракт.
3. Соберите сценарий из существующих частей. Если чего-то не хватает, расширьте
   подходящий контракт или оставьте новую ответственность локальной до появления
   подтверждённой потребности в совместном использовании.
4. Проверьте сценарий и затронутые границы. Существующие команды перечислены в
   [корневом README](../../README.md#checking-it); backend описан
   [отдельно](../../backend/README.md). `pnpm verify` не запускает все backend
   и браузерные проверки.
5. Проверьте стоимость следующего изменения: общая замена реализации, отличие
   одного экрана, временный адаптер. Добавляйте точку замены там, где эти сценарии
   нужны; не создавайте интерфейс для каждой функции.

## Критерии простоты при ревью

- Для изменения одного правила есть одно понятное место.
- Новая фича не копирует уже существующую обработку ошибок или инфраструктуру.
- Контракт принимает только необходимые зависимости и не раскрывает внутреннее
  состояние всего экрана.
- Абстракция уменьшает объём знаний потребителя; число файлов само по себе
  не служит показателем качества.
- Пример и тест показывают реальное использование, включая неуспешный сценарий.

## Следующая область аудита

В [useAuthOperations](../../frontend-app/src/views/authentication/model/useAuthOperations.ts)
собирается большой объект состояний и setters для
[AuthOperationsState](../../frontend-app/src/views/authentication/model/authOperations.ts).
Это кандидат на разделение по самостоятельным сценариям, а не готовый эталон
для новых фич. Перед изменением нужно сопоставить переходы состояния, потребителей
и тесты, затем проверить, какие механизмы уже предоставляет `Form`.
Наличие ручного фокуса само по себе ещё не доказывает, что его можно удалить.

Карта описывает проверенные точки входа, а не полный аудит качества или готовности
продукта. При изменении публичного пути обновляйте соответствующую ссылку.
